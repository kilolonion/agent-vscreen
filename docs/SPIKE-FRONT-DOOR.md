# 验证方案：把入口放进 Shizuku 用户服务

这是一份还没有做的验证方案。1.2.0 没有改这一部分，入口仍在 App 进程里。

## 要解决的问题

现在 HTTP 入口和命令执行都在 App 进程里。系统在后台冻结或杀掉 App 进程时，agent 的连接会断，盯守会停。1.1.3 起用前台服务、保活和端口重试缓解了这个问题，但各厂商系统的后台策略不同，没有办法保证。

Shizuku 用户服务是以 shell 身份运行的独立进程，不受应用后台策略管。如果把入口放到那里，App 界面进程被冻结也不影响 agent。

## 为什么没有直接做

这件事的可行性取决于真机上的行为，在没有手机的环境里无法判断：

1. shell 身份的进程能不能监听本机端口并让其它应用连上。不同系统的 SELinux 策略不一样。
2. 用户服务进程在 App 被冻结、被划掉、被强制停止时各自还活不活。Shizuku 的文档说服务会随 App 被杀而结束，除非以守护方式启动，各版本行为有差别。
3. 文字识别、无障碍信息、悬浮窗、通知都依赖 App 进程。入口搬走以后，这些能力要通过进程间调用回到 App，App 被冻结时调用会卡住。也就是说只搬入口不够，感知也要能在服务进程里独立工作。
4. 内置的 Tailscale 节点需要 App 的网络权限和存储目录，shell 身份没有。

第 3 点决定了工作量：如果感知离不开 App 进程，搬入口就只能解决“连接不断”，解决不了“命令能做完”。

## 验证步骤

按顺序做，每一步有明确的通过条件。前一步不通过就停下，不做后面的。

### 第 1 步：服务进程能不能当入口（半天）

在用户服务里开一个只回 `ok` 的本机端口。

- 从 Termux 和另一个普通应用访问，能连上。
- 在两台不同厂商的手机上都成立。

不通过：方案不可行，记录原因，结束。

### 第 2 步：服务进程能活多久（半天）

保持第 1 步的端口，分别做下面的事，每次之后隔 1、10、60 分钟访问端口：

- App 退到后台并息屏。
- 在最近任务里划掉 App。
- 在系统设置里把 App 设为受省电限制。
- 在系统设置里强制停止 App。
- 重启 Shizuku。

记下每种情况下服务还在不在。通过条件：前三种情况下 60 分钟后仍在。后两种不要求。

### 第 3 步：没有 App 进程时能做什么（1 到 2 天）

在服务进程里只用它自己有的能力做一遍“看 → 做 → 核对”：

- 截副屏的画面：能。
- 注入点击和按键：能（现在就在这里）。
- 读控件信息：试 `UiAutomation` 在 shell 身份下能不能取到副屏的窗口内容。
- 文字识别：试把识别模型放进服务进程加载，记下内存和首次耗时。

通过条件：App 进程被冻结时，一段 `act "tap 字; type 字; wait text:字"` 能在服务进程里完整做完，耗时不超过现在的 1.5 倍。

### 第 4 步：决定怎么分

按第 3 步的结果三选一：

- 感知全部能在服务进程里做：入口和执行都搬过去，App 只剩界面、确认弹窗和通知。
- 只有部分能做：入口搬过去，命令进来时如果 App 进程不可用，先把它拉起再执行，返回里说明等了多久。
- 都做不了：不搬，继续走保活。把结论写进 API.md 的已知限制。

## 需要的东西

- 两台不同厂商的真机，其中一台是后台限制较严的系统。
- 每台手机上能改电池设置、能看 logcat。
- 大约 3 到 4 天。

## 在此之前

确认弹窗、令牌管理、操作日志这些 1.2.0 新加的东西都在 App 进程里。入口搬走以后，它们和入口之间要多一层调用，这部分在第 4 步定下方向之后再设计。
